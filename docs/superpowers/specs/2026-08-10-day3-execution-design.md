# CatstepCoach Day 3 任务执行设计

## 目标

把 Day 2 生成的计划预览转化为经过身份认证、由用户明确确认的正式今日计划，并让 Today 页面能够使用该计划执行任务和记录难度反馈。

## 范围

Day 3 按依赖顺序分为三个功能切片：

1. 每个已认证用户在每个本地自然日确认并持久化一份今日计划。
2. Today 页面加载已持久化的计划，并允许用户在确认前编辑计划预览。
3. 开始和完成任务，同时记录 `easy`、`just_right` 或 `hard` 难度反馈。

提醒、逾期任务缩小、晚间复盘、长期记忆、成长值、额度和部署不属于 Day 3 范围。

## 选定的系统边界

新增一个 `plan-confirm` CloudBase 云函数。客户端提交编辑后的 Day 2 计划预览、请求 ID 和原始可用时长约束。服务端负责：

- 从 `WX_OPENID` 获取可信身份；
- 使用共享的每日计划校验器再次校验完整计划；
- 验证计划引用的每一个活动目标都属于当前调用者；
- 生成 `Asia/Shanghai` 日期以及全部归属、状态、ID 和时间戳字段；
- 以原子方式返回已有计划，或为当天创建一份使用确定性文档 ID 的计划；
- 保存一份包含内嵌任务状态的 `plans` 文档，并且不覆盖并发请求中已经胜出的计划。

该方案遵守“AI 负责推荐，用户负责确认”的产品原则。如果在 `plan-generate` 中直接持久化，会把尚未确认的预览保存为正式计划；如果允许客户端直接写数据库，则会削弱归属校验和幂等控制。

## 持久化数据结构

确认后的计划保存 `_openid`、`owner`、`date`、`availableMinutes`、`summary`、`tasks`、`status: "confirmed"`、`requestId`、`version: 1` 和 `createdAt`。

每项任务保留通过校验的计划字段，并增加由服务端生成的确定性 `id`、数字 `priority` 和 `status: "pending"`。

客户端不能提供归属、日期、任务 ID、任务状态、优先级、计划状态、版本或时间戳。

## 对外错误

- `UNAUTHENTICATED`：没有可信的微信身份。
- `INVALID_CONTEXT`：计划格式错误、时长无效，或引用了不属于调用者的目标。
- `INTERNAL_ERROR`：仓库发生意外错误；响应不得包含内部细节。

## 测试策略

所有行为严格遵循红—绿—重构：

- 服务测试覆盖输入校验、目标归属、每日幂等、可信持久化字段和确定性 ID。
- Handler 测试覆盖身份认证和稳定的公开错误。
- 结构与构建测试验证可部署的 CommonJS CloudBase 入口。
- 后续功能切片继续补充客户端传输、Today 页面状态和任务更新测试。

## 成功标准

1. 已认证用户能够为当前上海日期确认一份有效的 Day 2 计划预览。
2. 重复确认同一天的计划会返回同一份计划，不会产生重复写入。
3. 外部用户或非活动目标的 ID 会在持久化前被拒绝。
4. 保存的归属、日期、任务 ID、状态、优先级、版本和时间戳全部由服务端生成。
5. 不新增任何凭证、AppID、环境 ID、私有配置或真实用户数据。
6. 聚焦测试、完整测试、类型检查、CloudBase 构建和空白字符检查全部通过。
